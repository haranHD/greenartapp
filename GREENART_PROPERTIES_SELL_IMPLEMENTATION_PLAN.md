## Security findings and implementation policies

- The public list currently filters by `Active` alone. Public detail and enquiry creation look up listings by ID without checking public eligibility. Apply one eligibility predicate to list, detail, map, media, new enquiries and favourites. Phase 2 should close the legacy creation and publication paths when seller eligibility is introduced, and use the same eligibility checks for the legacy buyer routes.
- The current shared listing response contains seller phone, address, survey number and exact coordinates. Use explicit public and private DTOs. The public response should use a locality centroid or configured coarse geography and exclude private fields. Public search must also exclude survey numbers. Apply the same public geography to spatial filters so query results cannot reveal exact coordinates through repeated boundary queries.
- Seller suspension hides existing listings immediately through the public eligibility predicate and blocks seller mutations. Preserve listing rows and review history. Reinstatement requires an explicit admin decision. Reconfirm publication before previously suspended inventory returns.
- A material change to a published listing moves it out of the public feed until review. Separate moderation from sale status and enforce both transition policies in the domain. Protect edits and decisions with an expected version and transactional audit writes. Coordinate approval checks and protected writes so a concurrent suspension cannot authorize a later mutation.
- Enquiries require an active authenticated buyer and an eligible listing. Enforce length limits, per-user throttling and storage-backed duplicate protection that also works under concurrency. Limit seller access to enquiries on listings they own. Return contact fields only under an explicit sharing policy. Use report and enquiry queues for admin moderation.
- Validate upload lengths, counts and actual content. Store uploads under server-generated keys, strip photo metadata, and use owner/admin authorization for verification documents. Public image access requires eligible publication. Stage uploads and clean up failed or unreferenced objects.
- Treat a legacy verified flag and legacy listing status as historical data. Preserve those values during migration and require explicit approval for seller privileges and review of legacy inventory before public display. Confirm the rollout impact on current inventory during plan review.

## Incremental implementation

### Phase 2 · Seller approval backend

- Add seller application, profile and transition rules under `backend/Greenart.Domain/Entities/` and `backend/Greenart.Domain/Enums/`, with contracts under `backend/Greenart.Application/DTOs/`. An absent profile reads as `NotApplied`. Keep the application submission history and each review's actor, timestamp, decision and reason. Separate applicant-visible feedback from internal notes.
- Add EF mappings in `backend/Greenart.Infrastructure/Persistence/Configurations/`, sets in `backend/Greenart.Infrastructure/Persistence/LandPriceDbContext.cs` and an additive migration in `backend/Greenart.Infrastructure/Migrations/`. Use user foreign keys, one profile per user, one open application per user, a review queue index, and concurrency protection on decisions. Reuse `backend/Greenart.Domain/Entities/AuditEvent.cs` for transactional audit capture, keeping sensitive application contents out of generic audit details.
- Register `POST /api/v1/sellers/apply`, `GET /api/v1/sellers/me`, `PATCH /api/v1/sellers/me/application`, and the admin list, detail, decision and suspension routes from the brief. Review decisions require a live administrator account and disallow self-review. Gate the legacy marketplace endpoints in `backend/Greenart.Api/Program.cs` before adding any further listing mutation.
- Test state transitions, duplicate applications, applicant access, pending and suspended sellers, self-approval, non-admin review, stale decisions, audit persistence and legacy visibility.

### Phase 3 · Listings, media and buyer workflows backend

- Extend `MarketplaceListing.cs` with independent sale status, moderation transitions, editable draft data, publication timestamps and concurrency version. Add media, favourites, reports, price history and moderation history with foreign keys and targeted indexes. Store structured features with the listing unless they need independent querying.
- Add public geography, keep legacy exact points private and backfill public points only where their accuracy can be established. Derive rates from decimal canonical area and asking price using `LandArea.cs`. Recompute compatibility columns atomically while legacy consumers still use them. Record the original asking price and every change. Track duplicate candidates for review and exclude duplicate inventory from any future separately labelled asking-price benchmark.
- Extend the existing marketplace route family. Keep deployed paths during client migration and map any new property aliases to the same handlers and authorization. Add draft create/edit/submit, owner sale status, media, buyer discovery/map/favourites/enquiry/report, seller enquiry management and admin review APIs. Apply bounded pagination and deterministic sorting.
- Add regression coverage for ownership, moderation, sale status, pricing and conversions, private field redaction, geo filters on PostGIS, concurrent updates, media access, reports, favourite privacy and duplicate enquiry prevention. Assert that neither listing approval nor sale status produces valuation evidence.

### Phase 4 · Sell mobile

- Update `apps/mobile/src/components/SellLandFlowView.tsx`, `apps/mobile/App.tsx`, `apps/mobile/src/services/api.ts` and the shared contracts. Show application and correction forms and appropriate feedback for each seller state. Approved sellers can view drafts, reviews, published inventory, sold/withdrawn inventory and their enquiries.
- Connect the five-step wizard to persisted drafts and the upload workflow. Support cover photo and order, private verification files, validation, preview, submit and reopening for edit. Keep seller controls tied to the latest server eligibility.

### Phase 5 · Properties mobile

- Extend `apps/mobile/src/components/PlotMarketplaceView.tsx` and `apps/mobile/src/components/PlotDetailModal.tsx` for server filters and pagination, a list/map toggle, gallery, favourites, enquiries and reporting. Show seller review scope and clarify asking-price status. Reuse the existing map adapters and violet-and-gold theme.

### Phase 6 · Admin console

- Add Seller Management to `apps/admin-web/src/App.tsx` and extend `apps/admin-web/src/components/ListingModerationView.tsx` using typed requests in `apps/admin-web/src/services/api.ts`. Add filters, detail review, private media access, map, moderation notes and history, price changes, reports and enquiry inspection.

### Phase 7 · Integration verification

- Run the full registration, application, approval, draft, submission, publication, discovery, enquiry, enquiry management and sold-status workflow against a disposable test database with PostGIS. Exercise suspension, stale edits, and authorization failures. Confirm the workflow leaves verified transaction inputs unchanged and regressions are covered in the existing backend test projects.
- From the repo root, run `dotnet test backend/Greenart.sln`, `npm run test --workspace @greenart/mobile`, `npm run build --workspace @greenart/mobile` and `npm run build --workspace @greenart/admin-web`. The admin package currently has no separate test script. Add the requested admin workflow coverage and record its command when introduced.
- Record changed paths, migration and route changes, exact commands and results, remaining issues and the next phase after each increment. Use additive migrations on a disposable database first. Production rollout and destructive changes require separate approval.
